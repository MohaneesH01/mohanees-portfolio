A microcontroller that sees solar faults.

Edge Sentinel runs a quantized TFLite-Micro (int8) on-device classifier on a $4 ESP32. It distinguishes six fault modes — open circuit, partial shading, temperature anomaly, current deviation, sensor failure, and normal — under real-world conditions of irradiance variability, temperature drift, and sensor aging.

"Practical fault detection is achievable within microcontroller-class constraints — with direct implications for off-grid and developing-region solar deployments."

02 · Method

Why these choices?

Six engineering decisions that define Edge Sentinel — and the alternatives I considered.

/01

Why ESP32 over Arduino Uno?

Uno has 2KB RAM and no WiFi — can't run TinyML or network. ESP32 gives 520KB usable RAM, WiFi+BLE on-chip, and a mature Arduino + ESP-IDF toolchain, for $4 retail. STM32 (F4) is the right production target (v2); v1 chose ESP32 because of the integrated wireless stack.

/02

Why MQTT instead of HTTP?

HTTP carries 200-800 bytes of header per ~100-byte payload — 80% wasted bandwidth. MQTT is pub/sub, ~10 bytes overhead, native to IoT brokers. Edge Sentinel publishes telemetry at 0.33Hz with QoS 0; QoS 1 reserved for fault alerts.

/03

Why TinyML on-device, not cloud?

The target deployment is rural rooftop PV where connectivity is intermittent or absent. Cloud inference fails the use case. On-device inference runs in under 50ms with zero network dependency; data stays on the panel.

/04

Why five detection methods compared?

Honest benchmarking requires same train/test split, same dataset, same metric. The literature shows rule-based often wins on edge — we test that claim. Centroid is the on-device approximation of Random Forest.

/05

Why temperature-scaled calibration?

Without calibration, on-device confidence is meaningless — distance metrics don't map to probability. Temperature scaling converts logits to calibrated probabilities with a single learned scalar T. v2 will report ECE on the held-out test set.

/06

Why audit-grade explanations?

Safety-critical infrastructure requires per-decision traceability. Each prediction is paired with a rule trace, per-feature Z-score attribution, and a calibrated probability — one JSON line per reading, deployable on Serial or MQTT.
